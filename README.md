# rhythm-4k

浏览器端四键下落式音游。读取 osu!mania 谱面包（`.osz` / `.zip`），解出谱面和音频，
让音符跟着音乐下落，并给出 osu!mania 的判定、连击和结算。

**纯前端，运行时零依赖。**

---

## 快速开始

```bash
cd rhythm-4k
npm install
npm run dev
```

浏览器打开 `http://localhost:5173`。把一个 `.osz` 拖进去，选一个难度，然后按
**D F J K** 打。

> 需要 **osu!mania** 谱面（`Mode: 3`）。osu!std / taiko / catch 的谱面会被自动过滤掉。

其他命令：

| 命令 | 作用 |
|---|---|
| `npm run dev` | 开发服务器（HMR） |
| `npm run build` | 类型检查 + 生产构建（多文件，适合部署到静态服务器） |
| `npm run build:portable` | 同上，再把产物内联成**单文件 HTML**（双击即可游玩） |
| `npm run typecheck` | 只做类型检查 |
| `npm test` | 冒烟测试（解析 / 判定 / 缓存 / 倒计时 / 庆祝动画 / 下落样式，共 208 项断言） |
| `pwsh tools/make-fixture.ps1` | 可选：用 PowerShell 生成一份真实 zip 作为交叉验证素材 |

### 两种构建产物，用哪个？

| 产物 | 怎么用 | 限制 |
|---|---|---|
| `dist/`（`npm run build`） | 用静态服务器指过去 | 必须走 HTTP |
| `dist-portable/index.html`（`npm run build:portable`） | **双击就能玩** | 保存谱面到磁盘这功能会降级 |

**为什么默认构建不能双击打开**：Vite 产出的是 `<script type="module" src="...">`，
而浏览器**禁止从 `file://` 加载 ES 模块**（模块一律走 CORS 检查），双击会白屏。
`build:portable` 把 JS/CSS 直接内联进 HTML、并且用**经典脚本**（不是 module）内联，
绕开了整个模块解析流程。

`tools/inline-dist.mjs` 会自检：产物里不能残留任何外部引用、不能残留 `type="module"`、
核心 DOM 必须齐全 —— 不满足就直接报错，而不是产出一个"能生成但跑不起来"的文件。

> 单文件版在 `file://` 下音画同步、判定、倾斜、按键音这些核心玩法完全正常，
> 但**保存谱面到磁盘会用不了**（File System Access API 在 `file://` 下不可用），
> 会自动降级到浏览器存储。

## 游玩区尺寸

游玩区的尺寸由**两个独立的旋钮**决定，调大游玩区两个都要看：

| 旋钮 | 在哪 | 当前值 |
|---|---|---|
| 画布多大 | `style.css` 的 `.stage` 高度、`body.is-playing .app` 宽度 | 高 `clamp(420px, 78vh, 820px)`，宽最多 1240px |
| 轨道在画布里占多大 | `core/fall-style.ts` 的 `computePlayfieldWidth()` | 画布宽的 72%，再按单轨 110–200px 夹住 |

为什么需要第二个旋钮：**画布变宽并不会自动让轨道变宽**。单轨宽度有 200px 的上限，
否则在超宽屏上四条轨道会被拉得极开、眼睛要来回扫。

**硬约束**：轨道区域最多占画布宽的 86%。因为倾斜时判定线**以下**会向外张开
（80° 时底部比判定线处宽约 12%），不留这个余量轨道就会顶出画布。
单元测试对 320–2560px 画布 × 4/5/6/7K 的每个组合都检查了这一条。

实际效果（4K）：

| 画布宽 | 轨道区 | 单轨 |
|---|---|---|
| 700px | 504px | 126px |
| 868px（旧版布局） | 625px | 156px |
| 1208px（新版布局） | 800px | 200px |

游玩时容器会从 900px 放宽到 1240px。导入和选难度那两页的内容是一列列表，
太宽反而难读，所以只在播放面板显示时放宽（`body.is-playing`）。
容器一变宽，`.stage` 跟着变宽，引擎的 `ResizeObserver` 会自动重算布局和轨宽 ——
不需要任何手工同步。

## 信息栏

游玩区旁边可以显示一条信息栏：曲绘、曲名、曲师、谱师、难度名、BPM、音符数。
设置里可选**左侧 / 右侧 / 关闭**（默认右侧）。谱面里没有的信息统一显示「暂无消息」。

### 曲绘从哪来

osu 的曲绘写在 `.osu` 的 `[Events]` 段里：

```
[Events]
0,0,"bg, night.jpg",0,0
```

解析这一行有个坑：**不能简单地 `split(',')` 取第三段** —— 文件名里完全可能带逗号
（上面这个例子就是），那样会被切成两半。所以优先按引号取，取不到再退回简单分段
（很老的谱面不写引号）。测试专门用了带逗号的文件名来钉死这一点。

拿到文件名之后还要去压缩包里按名字找。名字大小写可能不一致、可能带子目录、
可能被 URL 编码过，所以是三级匹配。

和音频不同，曲绘**刻意不做「随便挑一张图」的兜底** —— 一个谱面包里往往还有一堆
storyboard 用的图片，随手挑一张只会更糟。找不到就显示「暂无消息」。

### 为什么用 Blob + object URL

曲绘动辄好几 MB，转成 base64 data URL 会膨胀三分之一，而且会一直躺在 DOM 属性里。
所以用 `URL.createObjectURL()`。

代价是**必须手动释放**：换歌或离开游玩界面时调用 `revokeObjectURL()`，
否则切几首歌就会攒下几十 MB 且不会被回收。

### 信息栏不能吃掉游玩区的宽度

信息栏占 240px + 16px 间距。如果容器不跟着加宽，它会直接吃掉轨道的宽度、把游玩区挤小 ——
那就和「把游玩区做大」的初衷正好相反。

所以 `style.css` 里做了两级放宽：

| body 类 | 容器宽度上限 |
|---|---|
| `is-playing` | 1240px |
| `is-playing` + `has-info-panel` | 1520px |

两个类都由 `syncLayoutClasses()` 统一维护。容器一变宽，引擎的 `ResizeObserver`
会自动重算布局和轨宽，不需要任何手工同步。

信息栏放左还是放右只用 `data-side` 切换 `flex-direction`，**不挪 DOM** ——
挪节点会重建 canvas 所在的子树，白白赔上一次引擎重算。

## 下落样式

播放界面的控制栏有两个切换按钮，设置面板里有对应的细调项。

### 倾斜轨道（透视）

一键在「垂直下落」和「倾斜轨道」之间切换。设置里还可以把角度调成 0–80° 之间的任意值，
两者共用同一个设置项，不会出现「按钮说是开的、滑条说是 0」这种矛盾状态。

倾斜的是**深度方向**：判定线在最近处（画面下方），轨道像一条向远处延伸的路，
越往上越远、越窄、音符越小。

核心是一条极简的投影公式。令 `u` 为归一化深度（`0` = 判定线，`1` = 一个下落距离之外），
`k = tan(倾斜角)`：

```
缩放系数   s(u) = 1 / (1 + k·u)
屏幕竖直位置 y(u) = 判定线Y × (1 - u) / (1 + k·u)
横向位置   x     = 消失点X + (轨道在判定线处的 x - 消失点X) × s(u)
```

三条性质值得注意：

- **`y(0)` 恒等于判定线Y，`s(0)` 恒等于 1。** 也就是不管倾斜多少度，
  音符时间一到都精确压在判定线上、且是原尺寸。这是倾斜不影响判定的保证，
  单元测试对 0°/5°/20°/40°/60°/80° 逐个钉死了这一点。
- **`k = 0` 时退化成完全正交**，也就是原来的垂直下落，行为一模一样。
- **因为 `x` 和 `y` 都是 `s` 的线性函数，而 `s` 又是 `y` 的线性函数，
  所以轨道边缘在屏幕上是直线** —— 轨道是个梯形，两个端点一连即可，
  不需要按段逼近。判定线本身始终水平且宽度不变（`s(判定线Y) = 1`），
  否则「音符压线」就没法一眼判读了。

这个模型还有个实际好处：**轨道只会向内收窄，永远不会斜出画面**
（判定线以下虽然会略微变宽，但最多 12%），所以 80° 可以完整生效，
不需要像水平剪切那样按窗口宽度削减。

### 角度上限为什么是 80° 而不是 90°

因为 `k = tan(θ)`，而 `tan(90°)` 是无穷大 —— 轨道彻底侧过去之后就"看不见"了。
80° 对应的强度是 `tan(80°) ≈ 5.67`，此时轨道最远处只有判定线处的 **15% 宽**，
已经是很极端的"虫洞"观感了。

角度和强度的关系是非线性的：

| 角度 | 强度 k | 轨道最远处宽度 |
|---|---|---|
| 20° | 0.36 | 73% |
| 40° | 0.84 | 54% |
| 60° | 1.73 | 37% |
| 80° | 5.67 | 15% |

大角度下有一个可以预期的取舍：远处音符在屏幕上被压得很小、也挤得很密，
**大部分屏幕位移集中在靠近判定线的最后一段**。这正是强透视该有的样子，
但阅读难度会明显上升。设置面板括号里显示的百分比就是给这个用的。

### 加速下落

加速感是**透视本身带来的**，没有额外的加速曲线。

音符沿轨道始终是匀速的（滚过多少像素由滚动模型决定），但投影到屏幕上之后，
远处的位移被压得很小、近处被放得很大。结果就是音符刚出现时在屏幕上慢慢挪、
靠近判定线时突然快起来 —— 和真实世界里「车从远处开过来」是同一个道理。

而且这种加速是**几何自洽**的：它和轨道的收窄、音符的缩小来自同一个投影，
三者在视觉上完全一致。这也是为什么这里不额外叠加一条加速曲线 ——
叠上去反而会显得别扭（等于把同一个效果做了两遍）。

### 音符形状

「圆形音符」按钮在方形和圆形之间切换。

两种形状都保证**最底端落在同一个位置**上，所以方变圆之后判定线的视觉位置完全一致，
不会觉得手感变了。

### 音符大小

设置里有 1–5 档，第 3 档是基准。档位表在 `core/fall-style.ts` 的 `NOTE_SIZE_PRESETS`。

**基准档刻意取成和加这个设置之前一模一样的值**，所以升级不会改变任何人现有的观感：

| 档位 | 宽度占轨道 | 厚度倍率 |
|---|---|---|
| 1 最小 | 60% | 0.55× |
| 2 较小 | 72% | 0.75× |
| 3 **基准** | **84%** | **1×** |
| 4 较大 | 93% | 1.3× |
| 5 最大 | 100% | 1.65× |

第 3 档的 `84%` 正好等于原来的「轨道宽度减去左右各 8% 的内边距」，
`1×` 就是原来的厚度。单元测试拿真实的轨宽验证了这一点 ——
它会在 60/90/120/156/200px 五档轨宽下，逐项对比「新公式」和「改造前的硬编码公式」是否完全一致。

两个设计约束：

- **宽度封顶在 100%。** 音符画得比轨道还宽会溢到隔壁轨道上，那看着就坏了。
  所以最大档的宽度正好占满轨道，再大的差异只能靠厚度体现（1.65×）。
- **宽度用「内边距」而不是直接拿比例去乘。** 这样能保住一个最小留白，
  轨道特别窄的时候音符依然不会贴到分隔线上。

长条主体、尾块、圆形直径都跟着同一档缩放，比例内部保持一致
（长条主体沿用原来的 `0.56 / 0.84 = 2/3`）。

## 按键音

按下轨道键时播放一个短促的敲击音。**完全用 Web Audio 现场合成，不加载任何音频文件** ——
一个 70ms 的衰减正弦就够了，不值得为它引入一个资源文件，而且合成出来的声音没有解码延迟。

### 延迟是这个功能唯一重点

声音必须在 **keydown 回调里当场播放**，绝不能等下一帧再统一处理。
等一帧就是最多 16ms 的额外延迟，而「按下到出声」的延迟是人耳最敏感的东西之一。

所以它绑的是**按键**而不是**命中**：空敲同样有声音。这是键盘反馈，不是判定反馈 ——
玩家需要听到自己明明按了。

具体到实现上有两处必须注意：

- `source.start()` 不传参数（= 立刻播放）。传 `ctx.currentTime` 反而会多走一层排期逻辑，
  那点排期在音乐上是必要的，在按键音上是纯损耗。
- 音量用一条常驻的 `GainNode` 控制，而不是每次重新生成 buffer —— 调音量时零重建开销。

### 音色

四条轨道用**五声音阶**的不同音高（A4 起）。之所以不用半音阶，是因为几条轨道经常会被
同时按下（和弦、连打），五声音阶里任意几个音一起响都不会难听；半音阶相邻的音一起响会非常浑浊。

音色是「指数衰减包络 × 基频 + 两个泛音」。加泛音是为了让它听起来像「敲」而不是「哔」。
另外有 1ms 的起音斜坡 —— 从 0 直接跳到振幅会在扬声器上「啪」一声，那不是敲击声，是直流跳变。

可以在设置里开关和调音量，改动时会自动试听一次（把所有轨道一起响一遍，正好是个和弦）。

## 全连击庆祝

整首一个都没漏时，最后一个音符判完的瞬间会弹出 **FULL COMBO!!!** 的庆祝动画：
全屏闪光 + 从中间向两侧展开的金色横幅 + 带回弹放大和发光外描边的文字，持续 2.6 秒。
结算页也会显示一个全连击徽标。

### 判据

```
最大连击 == 音符总数
```

任何一个 Miss 都会把连击清零，所以两者相等等价于整首没漏。长条中途松手同样算 Miss。

只在所有音符都判完的那一刻检查**一次**，之后再改判定结果也不会重来。

### 时间曲线

在 `src/core/celebration.ts`（纯函数，有单元测试）。三段结构：

| 段 | 时长 | 内容 |
|---|---|---|
| 闪光 | 170ms | 全屏白色，快速衰减 |
| 横幅 | 420ms | 从中心向两侧展开（三次缓出） |
| 文字 | 2600ms | 0.35 倍 → 回弹放大到 1 倍，末尾 620ms 淡出 |

放大用了 **back 缓动**（先冲过 1 倍再落回来）。线性放大看着很「廉价」，有回弹才有「砰」地弹出来的感觉 ——
测试里专门有一条断言峰值必须真的超过 1 倍，防止哪天改着改着退化成线性。

## 倒计时

谱面开始前、以及**暂停后恢复**时，都先空出一段时间让玩家把手指放到键位上。

关键点是：**这不是一个画上去的遮罩层，而是真实的前置时间。**

`SongClock.play(fromMs, leadInMs)` 会把音频的调度时刻往后推 `leadInMs`，
于是歌曲时间会从 `untilMs - leadInMs` 一路涨到 `untilMs`。
两种场景走的是同一套逻辑，只是终点不同：

| 场景 | `untilMs` | 倒计时期间的歌曲时间 |
|---|---|---|
| 谱面开始 | `0` | −3000 → 0 |
| 暂停恢复 | 暂停位置 `P` | `P−3000` → `P` |

倒计时期间：

- 音符已经在按正常速度下落（只是还没进入可视范围）；
- 判定引擎照常运行，此时按键只会被记成空敲，不会断连；
- 歌曲时间到达终点的那一刻，正好就是恢复播放的时刻。

所以倒计时和谱面是**同一个时间轴上的同一段**，不存在「遮罩消失后歌曲才开始」的衔接问题。

### 暂停恢复为什么要「倒带」

倒计时期间画面会**往回倒带**，而不是定格不动。这样玩家能重新看到接下来要打的音符，
不用盯着一个定格画面数三下。音频本身不会倒带，它只是在倒计时结束后从 `untilMs` 继续。

倒带带来一个必须一起处理的副作用：**已经打过的音符会重新落一遍**，看起来像在重打。
解决办法是渲染层跳过状态为 `NOTE_RESOLVED` 的音符（见 `Judge.noteStates`）。
顺带还解决了一个观感问题：中途松手断掉的长条会立刻消失，而不是继续慢悠悠落下去。

这里有个容易写错的地方：**跳过已判音符的判断必须放在提前退出（`break`）之后**。
`break` 依赖 `headY` 的单调性，提前 `continue` 会让循环永远退不出去。

### 其它细节

- **不能靠「歌曲时间 < 0」判断是否显示倒计时。** 即使把倒计时设成 0 秒，
  音频调度也会保留 120ms 余量（`MIN_LEAD_IN_SEC`），那 120ms 里歌曲时间同样是负数；
  而且暂停恢复的倒计时终点是一个正数位置，压根不在 0 附近。
  所以引擎传给渲染层的是「还剩多久」，而不是一个布尔标志。
- **计分板只在「还在倒计时 **且** 一个音符都没判过」时收起。** 谱面开头显示
  「0 分 / 100.00%」没意义；但暂停恢复时已经有判定记录了，收起计分板会让玩家以为分数丢了。
- **可以设成 0 到 10 秒**（0 = 关闭倒计时，恢复时立刻开始）。

倒计时的进位换算抽在 `src/core/countdown.ts`（纯函数）。这段最容易差一位 ——
典型症状是「3 跳到 2 的瞬间闪一下 1」，肉眼很难复现，所以边界值都被单元测试钉死了。

## 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript | 谱面解析和判定全是结构化数据，类型能省掉大量调试 |
| 构建 | Vite 8 | 零配置、HMR 快 |
| 音频 | Web Audio API | 唯一能做毫秒级调度的方案，`<audio>` 元素精度只有几百毫秒 |
| 渲染 | Canvas 2D | 四键同屏通常 < 600 个音符，2D 足够；瓶颈在特效不在渲染器 |
| 解压 | 自研 ZIP 读取器 | 浏览器已内置 `DecompressionStream`，省掉 fflate 依赖 |
| 可选后端 | C11 + Winsock2 | 见下方「可选的 C 后端」。不存在时前端自动回落，功能不减 |

`devDependencies` 里只有 vite、typescript，以及测试用的 fake-indexeddb。**前端运行时零依赖。**

冒烟测试不需要浏览器，直接跑 Node（Node 22.6+ 原生支持执行 TypeScript，只做类型擦除）。
IndexedDB 那部分用 `fake-indexeddb` 顶上一个符合规范的实现，所以缓存代码是**真的被执行过**的，
而不只是通过了类型检查。

## 核心一：为什么下落位置要用积分算

教科书公式是：

```
y = 判定线Y - (音符时间 - 当前时间) × 速度
```

**这个公式只在速度恒定时成立。** 一旦允许下落时间随时间变化（速度是时间的函数
`speed(t)`），就必须换成累积积分：

```
y = 判定线Y - ( S(音符时间) - S(当前时间) )
其中 S(t) = ∫₀ᵗ speed(τ) dτ
```

直觉：音符的屏幕位置取决于**它和现在之间累积滚过了多少距离**，而不是
「时间差 × 某个速度」。

这个模型有一个非常漂亮的性质：

> 当 `音符时间 == 当前时间` 时，`S(音符时间) - S(当前时间) = 0`，
> 音符正好落在判定线上 —— **无论中途速度怎么跳变都不受影响**。

也就是说，视觉上的变速演出完全不会影响判定时刻。判定永远只由音符时间和
音频时钟决定。

实现上不必真的做积分：`S` 是分段线性的，预先算好每个分段起点的前缀和之后，
任意时刻的 `S` 都是一次查表 + 一次乘加，复杂度 O(log n)。

**代码位置**：`src/core/scroll.ts`。
**接入谱面 SV 的唯一位置**：`Engine.rebuildScroll()` —— 把倍率乘进速度里就够了，
积分、剔除、渲染代码一行都没动。

### 两层参数

| 层 | 含义 | 谁决定 |
|---|---|---|
| 基准下落时间 `T_base` | 音符从顶部落到判定线要多久 | **玩家**，设置里的滑条 |
| 谱面 SV `sv(t)` | 相对倍率，1.0 是原速 | 谱面解析得出（osu 绿线） |
| 实际速度 | `speed(t) = 判定线Y / T_base × sv(t)` | 两者相乘 |

设置里的「忽略谱面 SV」可以把第二层关掉，得到完全均匀的下落速度。

## 核心二：判定

### 判定窗口

用 osu!mania 的公式，从谱面的 OverallDifficulty 推导：

```
MAX   : 16ms（固定）
300   : 64 - 3 × OD
200   : 97 - 3 × OD
100   : 127 - 3 × OD
50    : 151 - 3 × OD
MISS  : 188 - 3 × OD
```

**代码位置**：`src/core/judge.ts` 的 `windowsFromOverallDifficulty()`。
要换一套手感，改这一个函数就够了，判定逻辑本身不关心具体数值。

### 三条不能违反的规则

**1. 判定必须用按键事件自己的时间戳，不能用渲染帧的时间。**

`KeyboardEvent.timeStamp` 和 `performance.now()` 在同一条时间轴上，是「这一下发生在
什么时候」的唯一可信来源。用帧时间会引入 0~16ms 的随机误差，而 MAX 窗口只有 ±16ms ——
等于把最好的判定随机抹掉。

所以每帧的顺序是**固定的**：

```
① 处理这一帧收到的按键（用事件自己的时间戳换算歌曲时间）
② 推进判定（扫描过期音符、结算按到底的长条）
③ 读时钟拿当前歌曲时间
④ 渲染
```

① 必须在 ② 之前。反过来的话，那些「其实在过期前就按下去了、只是事件晚到一步」的按键
会被扫描出的 Miss 吃掉。为了让这个窗口更安全，扫描过期音符时还额外多等
`INPUT_GRACE_MS = 50ms`。

**2. 同一轨上的音符必须按时间顺序判，不能挑「偏差最小」的那个。**

这是音游里不能违反的规则。如果允许挑最接近的，一串同轨连打（jack）就会全被算到
后面那个音符上，前面直接变成 Miss —— 手感会彻底错乱。

**3. 空敲不断连。**

按键时附近没有音符只计数、不惩罚。手抖一下就毁掉连击是不可接受的。

### 屏幕上的判定反馈

判定结果**集中显示在画面中轴、连击数字的下方**，而不是按轨道飘在判定线上方 ——
轨道一密就糊成一片，看不清自己这一下到底打得怎么样。

比 MAX 差的时候，下面再补一行 **FAST / LATE**，直接告诉你打早了还是打晚了：

```
        [ COMBO 123 ]      ← 大号、半透明，垫在音符下面
          [  MAX  ]        ← 判定结果，按等级上色
          [ FAST  ]        ← 只在比 MAX 差时出现
```

三行的位置都由 `judgementLayout()` 统一算出来，不会几处各写一份慢慢对不齐。

两个实现细节：

- **判定结果画在音符上面，连击数字却垫在音符下面。** 判定结果是关键反馈，
  被音符切开会很难读；连击数字又大又淡，垫在下面反而是好事。
- **符号约定是全局统一的：正数 = 打早（FAST），负数 = 打晚（LATE）。**
  单点音符和长条收尾都必须遵守。这条一旦不一致，延迟校准的平均值会被长条样本
  往反方向拉，FAST/LATE 也会显示反 —— 所以单元测试专门盯了这一条
  （早打 → 正、晚打 → 负、早松手 → 也为正、两者都打准时均值接近 0）。
- **偏差恰好为 0 时不显示方向。** 那种情况通常是音符压根没被按过、直接被扫成 Miss，
  方向无从判断，硬猜一个反而会误导玩家。

长条头部和收尾各推送一条反馈记录。收尾这条以前被抑制掉了（"同一轨不重复飘字"），
但那是在按轨道飘字的时代的优化 —— 现在只有一处集中显示，抑制掉就意味着
**长条松手打得怎么样永远看不到**，而最终评级恰恰是取两者中较差的那个。

### 长条

- 头部命中后进入「保持中」，**不在此时结算**（要等尾部）
- 一直按到结尾 → 送满评
- 提前松手 → 按「离结尾差多久」评级；超过 MISS 窗口就整条断掉
- 最终评级取**头部和尾部里较差的那个**，所以头部打得差依然会被惩罚

## 核心三：按键映射

- 绑定用 `KeyboardEvent.code`（**物理按键位置**）而不是 `key`（字符）。
  切换输入法、打开大写锁定、换键盘布局都不会失效。
- 按到已被占用的键时**自动对调**两条轨道 —— 拒绝的话用户得先想办法清空那条，非常别扭。
- 修改后立刻写入 `localStorage`，不需要点保存。
- 捕获按键时用**捕获阶段**监听 + `stopPropagation`，同时关掉游戏输入，
  保证这一次按键不会被判定引擎收到。
- 不同键数有各自的默认键位（4K → D F J K，7K → S D F 空格 J K L……）。

**代码位置**：`src/core/input.ts`（输入与格式化）、`src/store/settings.ts`（持久化）、
`src/ui/app.ts` 的 `captureKeyDown()`（捕获交互）。

## 延迟校准

结算页会显示本局的**带符号平均偏差**。如果这个数字稳定地偏离 0，就说明存在系统性延迟
（音频输出延迟、或者 MP3 的编码器补零）。点「用平均偏差修正音频偏移」即可一次修正。

推导过程：

```
offset      = 音符时间 - 实际命中的歌曲时间
实际命中时间 = f(按键时间戳) + audioOffsetMs
所以要让平均 offset 归零，只需  audioOffsetMs += mean(offset)
```

样本少于 20 个时不给修正按钮 —— 样本太少平均值不可信。

## 谱面存档

导入成功的谱面包会被存下来，下次打开页面直接在列表里点开，不用重新拖文件。

有两条路径，**磁盘文件夹优先**：

| 路径 | 什么时候用 | 存在哪 |
|---|---|---|
| **存档文件夹** | 浏览器支持 File System Access API（Chrome / Edge） | 用户选定的磁盘文件夹，比如工作区的 `save/` |
| 浏览器存储 | 不支持上面那个 API（Firefox / Safari） | IndexedDB，功能降级 |

### 为什么不能直接写死一个路径

浏览器的沙箱里，网页**不能**写入任意本地路径。想让 `.osz` 真正落到磁盘上某个文件夹，
唯一可行的办法是让用户手动选一次文件夹并授权 —— 这就是 File System Access API。

顺带说明：**「剪切」在这里做不到**。网页既不知道源文件在哪，也没有权限删它，
所以实际行为是「往存档文件夹里写一份」，用户原来那份不受影响。

### 存档文件夹这条路

- 文件夹句柄（directory handle）可结构化克隆，只能存 IndexedDB。
  但它只是一条几十字节的记录，**完全不占谱面体积** —— 谱面本体全在磁盘上。
  这也是整个功能里唯一还碰 IndexedDB 的地方。
- **同名文件会被覆盖**。重新导入同一首歌是期望行为，不会攒出一堆重复。
- Chrome 对写入权限很谨慎：句柄能跨会话记住，但**写入权限通常每次重新打开页面
  都要再确认一次**，而且 `requestPermission()` 必须在用户手势里调用。
  所以「恢复句柄」和「申请权限」是两个函数，界面上也分成两种状态 ——
  权限没拿到时列表区域会提示点「重新授权」，而不是干等着。
- File System Access API 还没进 TypeScript 的 lib.dom（或只进了一部分，
  不同 TS 版本覆盖程度不一样）。所以 `save-folder.ts` **自己声明了用到的那几个成员**，
  只在边界处做一次类型断言 —— 升级 TypeScript 不会突然编译不过。

### 浏览器存储这条路（退路）

存的是**压缩包的原始字节**，而不是解析后的谱面加解码后的音频。原因是体积最小 ——
`.osz` 本来就是压缩过的，展开成 PCM 音频要大几十倍；而且解析器以后改进了，
缓存条目会自动跟着受益。

两个容易踩的点：

**① 用两个 object store。** IndexedDB **读记录时整个 value 都会被反序列化**。
如果元信息和几十 MB 的 ArrayBuffer 放在同一条记录里，那么为了列个表而遍历一遍，
就会把所有谱面包的字节全读进内存。

| 表 | 内容 | 什么时候读 |
|---|---|---|
| `chartSetMeta` | 名字、大小、时间戳 | 列表页只读这张，非常便宜 |
| `chartSetBlobs` | 真正的字节 | 只在用户点开某一条时才读 |

**② 容量控制。** 单个超过 64 MB 不缓存（谱面包里塞视频很常见）；总预算 200 MB、
条目上限 20 个，超出按 LRU 淘汰；写入遇到 `QuotaExceededError` 时清掉一半最旧的重试一次。

这条退路是**锦上添花**：隐私模式、配额不足、浏览器禁用 IndexedDB ——
这些情况都会安静地降级，绝不影响正常的导入和游玩。所以 `chart-cache.ts`
的所有公开函数都不向上抛异常，而是返回空值 / `false`。

淘汰策略被抽成了纯函数 `planEviction()`，可以脱离 IndexedDB 单独测试。
写入 / 读取 / 覆盖 / 删除 / 清空这条完整链路则由 `fake-indexeddb` 在 Node 里真实跑一遍 ——
像「`await` 之后事务自动提交、后续请求全部失败」这类陷阱，只有真的执行才会暴露。

## 几个容易踩的坑（代码里都标了注释）

1. **不要用 `<audio>` 元素的 `currentTime`** —— 精度只有几百毫秒。
2. **不要用 `setInterval` 驱动逻辑** —— 会累积漂移。必须用 rAF 读音频时钟。
3. **`AudioBufferSourceNode` 是一次性的** —— 不能暂停，只能 `stop()` 后重建。
4. **`decodeAudioData` 会掏空传入的 ArrayBuffer** —— 而我们的字节往往是整个 zip
   大 buffer 上的一个视图，传进去会让 zip 的其它文件全变成 0。
5. **`getOutputTimestamp()` 比 `currentTime` 落后一个输出延迟** —— 用前者做渲染，
   画面才和声音对得上。
6. **ZIP 本地文件头的 name/extra 长度可能和中央目录不一致** —— 必须回到本地头重新读。
7. **`HTMLElement.click()` 的事件会冒泡** —— 文件选择框不能放在拖放区内部。
8. **长条的最高点是它的「尾巴」而不是「头」** —— 时间越晚 y 越小，剔除方向别搞反。
9. **类型化数组的 buffer 类型参数** —— TS 5.7 起 `Uint8Array` 带泛型参数，
   裸写会退化成 `Uint8Array<ArrayBufferLike>`，没法直接喂给 `Blob()`。
10. **`event.repeat` 必须挡掉** —— 否则按住不放会变成连续打击。
11. **窗口失焦要松开所有键** —— 否则 Alt+Tab 切走回来，那个键会永远处于按下状态。
12. **PowerShell 按 ANSI 代码页读无 BOM 的 UTF-8 脚本** —— 中文注释会变成乱码，
   甚至吞掉后面的语句（`tools/make-fixture.ps1` 因此刻意只写 ASCII）。
13. **作者样式里的 `display` 会压过 `[hidden]`** —— HTML 的 `hidden` 属性是靠浏览器
   **默认样式表**里的 `[hidden] { display: none }` 生效的，而作者样式表的优先级永远高于
   默认样式表。所以只要别处写了 `.overlay { display: flex }`，`hidden` 就完全失效，
   页面会同时显示所有面板 —— 而且不报任何错。`style.css` 里那条
   `[hidden] { display: none !important }` 就是从根上堵这个洞。
14. **透视投影在判定线以下有极点** —— `(1-u)/(1+ku)` 在 `u = -1/k` 处分母过零，
   坐标会炸到 `1e18`。**只要一条 Canvas 路径里有一个这样的顶点，整条路径就画不出来**，
   表现出来是「长条音符按住一会儿之后整个消失」。所以深度必须夹住
   （见 `fall-style.ts` 的 `minimumDepth()`）。触发条件是「头部过线后又走了足够远」，
   因此只有够长的长条会中招 —— 短长条在极点到来之前就整条过线、被剔除掉了。
15. **可滚动容器里不能用 `align-items: center` 居中** —— 子项比容器高时，
   `center` 会让它从**上下两端同时溢出**，而滚动容器的「可滚动溢出区域」只包含
   下方那一边，**上方溢出的部分永远滚不到**。表现出来就是「设置项一多，顶部就没了」。
   正确做法是容器用 `align-items: flex-start`，居中交给子项自己的 `margin: auto` ——
   有富余空间时 auto 外边距会吸收掉、正常居中；空间不够时 auto 解析成 0，从头排起。

## 已知限制 / 未做的事

- 音频只支持浏览器能解码的格式。**flac 在部分浏览器上不支持**，会解码失败。
- MP3 有编码器补零（约 20–50ms 静音前导），会造成系统性偏移。
  优先用 `.ogg`/`.opus`/`.wav`，或者用结算页的偏差修正。
- 压缩包会被**整体解压**（包括里面的背景图和视频）。带视频的 `.osz` 会慢一些。
- 不支持 Zip64。
- 引擎本身支持任意键数，但界面调校是围绕 4K 做的。
- 没有做触摸屏 / 手柄输入（`InputManager` 已经是独立模块，加输入源不影响判定）。
